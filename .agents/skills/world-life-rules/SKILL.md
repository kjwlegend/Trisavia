# 居民生活规则设计

把一个生活意图转成能够发生、能够持续、能够看到真实结果的行为。用户对体验类型和范围的选择优先；本项目默认以生活体验为中心。不要因为已有几个 NPC 就把所有玩法写成它们的固定日程，也不要因需要物品就扩成制造／建造产业链。

## 先找真实基础

从当前项目 `AGENTS.md`、`docs/planning/session-registry.md`、`docs/planning/workstream-status.md` 和架构入口确认职责与已有能力。必要时窄读实际模块／目录；历史“已实现／未实现”与当前回执冲突时查清，不复制旧结论。

设计属于哪个 WS 就归哪个 WS，其他领域给明确依赖和接口，不替它重写规则。总指挥只调度；设计讨论不自动授权修改运行世界、注册真人 Agent、发钱、发送他人消息或发布。明确的新用户授权可扩展本次设计范围，不能把旧只读登记当永久阻止。

项目完成过的首例位于 [M3 生活行为 v1](../../../docs/workstreams/ws03-interaction/life-actions-v1/README.md)。需要理解项目已有做法时查相关章，不默认加载全包；这只是示例规格，数值／范围仍须核对现行原 WS。它不是当前运行状态来源。

## 从行为建立闭环

先写一句居民意图，如“我想上班赚钱”“我想听一次演出”。再逐项回答：

1. **做什么、在哪里、得到什么？** 产出可以是经历、关系、知识或状态恢复，不强制每件事发币／发物。
2. **得到的东西能做什么？** 物品要有可执行用途；钱要有消费场景；无物质奖励的兴趣体验也需有清楚结果。
3. **为什么会选择另一个行为？** 说明时间、成本、偏好、地点或结果差异；不靠强制日程让所有居民做相同步骤。
4. **能否从可达的起点开始？** 检查零余额、缺工具、资源满员、离线等退路，避免一切都依赖尚未拥有的物品／收入。

把行为列成表，然后为每项写足可实施的规则。按需使用 [行为卡与覆盖清单](references/coverage.md)，不是机械为每个小改动创建所有文档。多个行为共享规则时集中写一次，明确各自例外。

## 沿行为补齐世界

- **场所／地图：** 活动区、接近点、可达路线、容量与公共通路；沿现有世界／板块／场景／场所层级，不由建筑图片推定室内已经存在。最终坐标由地图作者产出并验证，不能伪造。新规则不覆盖已发布固定地图资产。
- **NPC：** 职责、偏好、当前状态、候选行为、无候选退路，以及服务在 NPC 离岗时的语义。先保证规则选择器实际有用；未来模型只规划，不绕过相同规则／成本／权限执行。
- **物品与美术：** 从行为反推必需物品；逐项写来源、用途、实例／堆叠、可转移／预留／消耗及图片轮廓。图、atlas、animation、map manifest 要有制作任务、所有者和验收状态。美术规格完成不等于素材已生成。
- **经济／状态：** 统一数值来源，明确钱与物的产生／消费、恢复途径、时长／额度及实际计时。数值是开发默认或已测结果要标清；不把模拟经历当外部模型成长。

新行为应能与旧行为组合。例如“工作所得购买门票 → 去听演出”，同时允许不参加工作也能通过其他已有路径获得同种体验。若特定活动并不需要物品、货币或 NPC，说明不适用，不为了清单强加。

## 衔接服务器与外部 Agent

浏览器只呈现权威事实，Simulation 执行已授权规则，外部 Agent 经 HTTP 异步提交有限意图。活动持续不能要求每秒调用模型；计划接受不能冒充实际完成。

需要多步时写清步骤与有限条件、总期限／资源上限、成功后续／失败停点、逐步重验、异步等待、取消和已生效效果。身体占用与远程等待分开。额外对象、支出或表达选择需要新的合法决定，不能用“自主”填补未授权动作。

为每项说明：开始／完成时分别扣什么；何时预留和释放；重试如何查同次结果；断线／重启／旧租约／价格或地图版本变化如何处理。原域裁决钱、物、关系，通用计划与动画不直接写这些状态。复用现有 Scheduler／事务／回执，公共机制确有缺口再交平台负责人。

同步提供机器行为条目：实际 operation 绑定、输入／结果 schema、条件、成本、时长、取消、当前可行动状态、指南版本与回执查询。尚未发布的接口明确标拟议，不给可运行的假 URL。

## 结果、日志与反馈

分别设计命令回执、当前进度、业务结果、历史经历和主观评价。结果显示真实获得／消耗／未完成部分，空结果可以是正常完成。角色感觉、理解或满意度只能来自其明确声明，不由旁观者编造。

复用原日志来源及权限：本项目主人可分页读自己的全部获准历史；他人只读最新 10 条获准公开记录，先验权后限量；普通移动／轮询／计划阶段不写成日记。来源撤权、跨 Agent 切换、历史覆盖缺口与延迟确认要有准确界面。主观评价与 Civic 提案／投票分别成立，不从频繁行为自动制造社会诉求或一票。

## 形成可调度交付

为当前设计交一份有明确入口的规格，复杂时分章；共同数值／ID 只维护一处。包含范围、已存在／新增、规则、资源制作清单、数据／接口语义、关键状态与风险、各 WS／设计／工程责任、依赖和可体验切片。

从一条真实闭环切起，每片同时提供可发现行为、权威执行、真实结果与人类可见入口。不要先做一堆无效按钮，再等“未来引擎”补全。验收聚焦实际风险：钱物唯一结算、持续授权、并发占用、未知结果恢复、地图／素材一致与日志权限。固定随机或时间夹具要注明，不能当真实居民证据。

完成前沿至少两种不同生活选择走读，再检查一条取消／离线／失败路径，核对所有物品来源与用途、引用、数值和待制作项。小改动缩小检查范围，不默认全量回归或独立多轮审查。代码实施的独审和发布要求仍以当前项目规则为准。

当用户授权交总指挥时，使用登记中的真实 threadId，发送实际文件入口、范围、派单责任、第一切片、明确未实现／待制作项及发布边界。未授权转交时仅交付设计，不自动联系其他会话。skill 自身不构成常驻调度或外部消息授权。
