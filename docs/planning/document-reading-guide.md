# 文档分层与维护约定

日期：2026-10-14 · 本次调整回应用户的产品可读性反馈，仅整理 Markdown。

## 阅读顺序

整体体验从[产品体验总览](../product/experience-overview.md)开始。每个工作流采用相同的四层顺序：

| 文件 | 读者要得到的答案 | 应包含 | 不放在这一层 |
| --- | --- | --- | --- |
| 01-user-stories.md | 谁使用，为什么使用，能做什么 | 具体情景、用户故事、可见结果、功能范围 | 接口编号、任务切片、数据一致性术语 |
| 02-features-and-flows.md | 功能怎样运作，前后如何衔接 | 操作与反馈、正常与主要异常、依赖的产品能力 | 数据库实现、完整故障矩阵 |
| 03-technical-design.md | 功能如何由系统实现 | 功能到模块/数据/接口的对应、本地与服务端职责、待选技术 | 重新定义产品范围或另建同域实现 |
| 04-delivery-plan.md | 按什么顺序交付 | 可演示的增量、原任务映射、输入、验收、失败处理 | 复制另一套详细任务卡或新增完成度 |

各层必须包含实质内容，不能只有目录和跳转。用户故事中的“完成”是将来的验收结果，不表示现在已有可运行产品。

## 与原详细规格的关系

原 `plan.md` 保留已审查的详细规则、概念契约和任务卡，作为精确查阅依据；原 `review.md` 及三轮记录保留当时的证据。本次不改写 74 张任务卡，也不把新的阅读层自动标记为经过旧三轮审查。

用户最新决定优先。四层文档应与详细规格一致；如果出现矛盾，应登记并同步修订，不能让读者凭文档发布时间猜。技术细则与任务完整字段仍只在原详细规格维护一份，四层文档使用说明和引用，不复制整段规格。

未来变更先说明对用户体验和功能范围的影响，再更新功能流程、技术方案和任务映射。影响原规格时，由所属稳定 WS 修订对应段落，统筹把相关消费方修改拆给各所有者；审查记录保留历史，不把旧复核结果冒充新变更复核。

## 维护与执行归属

用户对每个 WS 的反馈派回[登记](session-registry.md)中的原稳定 thread。总指挥只分发任务、管理会话/worktree 生命周期、协调依赖、跟踪进度和汇总结果；产品文档、技术文件和代码由独立执行会话编辑，不以总指挥自己的临时 sub-agent 替代已有 WS。

共享入口、索引和协作规范由统筹指定独立会话维护，本次指定 WS06；各流保留自己的业务文档所有权与他人编辑。完整规则见[开发协作规范](development-guidelines.md)，自动读取入口见根 [AGENTS.md](../../AGENTS.md)。正式开发后的 worktree、branch 和专门独立代码审查 thread 仍待分配，当前不启动实现。

阅读和维护仍按上述四层推进，不因协作规则改动重写原 74 张任务或五阶段。历史规划/可读性审查保留原证据；未来代码变更由专门独立审查 thread 审核，不能用历史通过或作者自己的 sub-agent 自审替代。

## 语言与篇幅

- 从具体的人、Agent、操作和结果开始。主人想看懂 Agent 的近况，是用户故事；“作为用户，我希望系统幂等”不是合适的产品表达。
- 功能说明写“关闭电脑后，下次还能查看尚可获取的变化”，技术层再解释同步进度与保留窗口。
- 建议、待选、未来扩展与本阶段范围明确区分。示例不能把候选活动、服务或视觉风格变成已确认选择。
- 一个文件解决一层问题；先用短段落解释，再用表格比较并列能力，避免一格塞入完整业务流程。
- 横向工作流按每个阶段提供支持，不写成第六、第七个产品里程碑。

## 审查范围

本次针对新阅读层检查三件事：读者能否说清功能、故事与详细规格是否一致、依赖与任务引用是否能衔接。独立阅读反馈和修订记录见[本次可读性复核](readability-review.md)。原三轮技术与产品规划审查见[历史审查总记录](review-ledger.md)。
