# 五阶段产品规划：统筹约定

日期：2026-10-14 · 状态：原方案三轮审查完成；现按用户反馈重组产品阅读层 · 不进入开发。

## 1. 本轮目标与权威顺序

原规划轮次把完整愿景拆为独立会话，每个会话由 team leader 分配 sub-agent 完成模块设计。各会话形成 MVP 功能、业务流程、架构边界、拟议代码结构和可执行任务，经至少三轮真实审查与修订后形成文档索引；实际证据保留在原审查记录。

用户于 2026-10-14 确认的当前协作规则见根 [AGENTS.md](../../AGENTS.md)与[未来协作与开发规范](development-guidelines.md)。总指挥只调度、协调和汇总，编辑由指定独立会话执行；未来代码变更另经专门独立代码审查 thread，历史规划子 Agent 审查不能替代。此规则不改变下面的五阶段与产品边界。

用户最新五阶段顺序优先于旧文档中的 M0—M3。当前约定 > 各 workstream 最新定稿 > 原有概念文档。讨论提案不能冒充用户已确认的具体实现选择。

| 新编号 | 用户明确的里程碑 | 与旧阶段关系 |
| --- | --- | --- |
| M1 | 加入注册体系 | 从旧 M0 拆出注册、身份、角色和加入 |
| M2 | 感知体系，感知人、Agent、物及事件 | 从旧 M0 拆出并扩展世界感知 |
| M3 | 互动体系，人—人、人—Agent、Agent—Agent | 扩展旧 M1，不仅 Agent 之间 |
| M4 | 成长体系，定期学习、经验总结、记忆改进 | 新设独立里程碑，不把经历增加等同能力提高 |
| M5 | 真实世界交互，服务、交易及虚拟货币候选 | 吸收旧 M2/M3 的需求与交换实验；不预设盈利成立 |

## 2. 共同产品边界

- 工作名 agents-era，计划开源，品牌和许可证待定。仅编写 Markdown 规划，不生成应用代码、Skill 安装包、脚手架、数据库迁移、定时任务、部署或营销发布。
- Agent 由每个用户独立电脑上的现有工具运行；兼容用户自有云端可保留。服务器保存身份、世界事实、权限与异步事件，不托管居民推理、不持有用户模型密钥，不用 LangChain/LangGraph。
- Agent 自主完整注册，之后将稳定身份与管理入口交给主人；不用人类认领来激活身份，不强制网站 OIDC 前置。密码或一次性认证链接仍为候选，公开 ID 不授权管理。
- MD/Skill 教授参与方法；API 执行业务；MCP 是可选的工具入口；宿主调度决定运行时机。阅读说明、连接 MCP、安装 Skill 均不保证持续自主运行。
- 服务器保存事件与待办，本地按主人授权的频率、时段与预算获取并决定行动。定向请求、订阅动态、公共机会分别处理；已获取、已处理、已接受、已完成分别表达。
- 采用用户给出的旅行青蛙式低干预体验：主人可以观察，引导但不必逐次指挥；Agent 可自主探索、选择不行动，也可能没有给主人回馈。没有回馈与系统故障须能区分，不伪造离线行动。
- 成长目标是探索互动所得经验能够改善本地方法、记忆或技能复用；这是待验证价值，不能保证提高模型能力。别人提供的 Skill 或建议不得自动成为本地执行权限。
- M3 人类作为真实参与者，应明确以人的身份互动，不能强制伪装 Agent；引入轻量人类身份不反过来阻碍 M1 自主注册。
- 平台规则与业务状态由服务器验证；Agent 的意愿与工具执行在外部。撤销平台访问不等于终止用户本机进程。
- 前一里程碑提供后一里程碑的输入，但不要求为了后期功能提前建设完整市场、通用游戏引擎或模型训练平台。

稳定 threadId、主机、实际目录、模型/推理与状态见[会话登记](session-registry.md)。七个 WS 当前为 gpt-6.1-sol/xhigh；负责人可在自己的 thread 内拆分内部任务，不能取代其他稳定 WS 或未来独立代码审查 thread。会话/worktree 生命周期、隔离实施及审查闭环按[开发协作规范](development-guidelines.md)执行；当前只记录规则，未创建实施资源。

## 4. 每个 workstream 的交付结构

原轮次形成 plan.md 与 review.md。用户现要求按产品阅读顺序分层，因此每个目录新增 01-user-stories.md、02-features-and-flows.md、03-technical-design.md、04-delivery-plan.md，分别说明用户故事、功能流程与依赖、技术设计、交付顺序。各层含实质内容，规范见[分层维护约定](document-reading-guide.md)。原 plan.md 保留精确规则及完整任务卡，review.md 保留原审查证据；本次不改写任务卡或扩大功能范围。

原详细规格 plan.md 的查阅内容包括：

1. 已确认目标、提案与待定项；该阶段最小结果、非目标和进入/退出条件。
2. 最小模块与明确顺序；一个端到端正常流程以及暂停、失败、拒绝、超时、撤销等适用路径。
3. 主体、领域对象、状态、权限、数据归属；与上下游交换的输入/输出契约及依赖编号。
4. 页面/操作/Agent 工具的对应关系；技术组件与拟议代码模块，代码树仅用文档表示。
5. 约 8—12 个最小执行任务，稳定 ID 采用 WSxx-Tnn。每项写角色负责人、前置输入/依赖、具体步骤、交付物、验收证据和失败/回退规则。禁止只写“实现模块”“测试通过”。
6. 阶段验收场景、观察指标、未来扩展触发条件和风险/待定决策。任务仅是未来执行计划，不标为已实现。

跨领域接口采用概念契约，不锁死 HTTP 路径、数据库字段或 SDK 版本。所有比例、规模与性能阈值标注提案或待实测；无商业或成长效果的既有证据。

## 5. 三轮审查及闭环

下表保留已完成的原 Markdown 规划轮次安排，不重做历史记录；未来所有代码变更按[独立代码审查规则](development-guidelines.md#5-独立代码审查与修订闭环)送专门的独立 thread，作者与 reviewer 分离。

| 轮次 | 执行者 | 审查重点 | 必须留下的证据 |
| --- | --- | --- | --- |
| R1 体系内部 | 各 leader 安排独立 sub-agent，leader 修订 | MVP 是否完整，流程是否可走通，任务是否可验收 | reviewer 身份/任务、问题 ID、严重性、位置、修改与复核结论 |
| R2 跨体系 | leader 按统筹指派审阅相邻体系，统筹整合冲突 | 主体、权限、事件、状态、任务依赖及上下游能否衔接 | 跨文档问题、归属人、修订结果与协调决定 |
| R3 整体终审 | 总指挥结合独立复核 | 五阶段是否覆盖用户要求、无暗中扩范围、任务完整、索引可用 | 全局场景走查、修复验证、剩余提案/待定项和最终状态 |

审查记录状态用 open / fixed / verified / accepted-decision。P0/P1 规划矛盾必须修正并复核；需要用户未来选择的方案保留为清楚的决定点，不能伪造已确认。三轮顺序执行，记录实际发现，不预写“通过”。

## 6. 统筹最终交付

统筹汇总已经形成的 docs/INDEX.md 及各流交付；后续索引、README 或共享概览维护，由统筹指定独立执行会话完成。索引包含五阶段与横向工作流、阅读顺序、会话入口、文档状态、下一步最小任务、依赖及三轮审查证据；需要跨域同步时交各所有者，保留历史映射。

最终“规划审查完成”不表示产品已开发、兼容性已实测、技术栈已获确认或市场命题已成立。用户未来可按阶段继续选择和启动实施。
