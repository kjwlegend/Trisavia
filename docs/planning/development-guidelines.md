## 1. 先确定归属，再分发工作

| 角色 | 实际责任 | 执行边界 |
| --- | --- | --- |
| 总指挥稳定 thread | 任务分发、会话/worktree 生命周期、依赖协调、进度跟踪、结果汇总 | 不直接编辑产品文档、技术文件或代码；不在自己 thread 下用临时 sub-agent 接替既有 WS 的归属工作 |
| WS01—WS07 稳定负责人 thread | 接收本流反馈，维护所属文档，未来实施所属任务并提供交付证据 | 可拆分本流内部任务；跨域修改派回相应所有者，不直接改别人的归属文件 |
| 指定共享规范维护会话 | 执行统筹指派的共享规范、索引等文档变更 | 本次由 WS06 执行；后续指派须写明范围，不默认把共享文档编辑留给总指挥 |
| 技术总监独立 thread | 安排多个内部 sub-agent 实际实施 M1 后端/非视觉，记录最小模块边界、实现选择和验证证据 | 明确各自文件/模块归属，保留并发文档；不接管各 WS 产品规则或推进未授权前端/远期功能 |
| 独立整合执行会话 | 在获授权范围整合已审查变更、处理冲突并验证 | 可以复用合适的独立执行会话；总指挥只调度，不能自己修代码 |
| 专门的独立代码审查 thread | 检查固定范围的代码变更、测试证据及修订复核 | 作者与 reviewer 分离；不以总指挥或作者的 sub-agent 自审代替该 thread |

## 3. 会话创建、恢复与归档

用户已授权统筹自主判断何时创建、调度、恢复和归档会话，常规生命周期操作无需每次再次询问。优先复用已有归属；原会话被归档且仍适合承担原任务时，可以恢复后继续。新增独立会话只在归属、隔离、专门审查或整合确有需要时分配，创建/恢复后更新登记。

当前七个 WS 还需接收用户反馈，均保留；规划任务完成或暂时闲置不构成归档理由。新执行/审查会话完成后是否保留，由统筹结合后续反馈和依赖判断。

归档前完成以下交接：

1. 保存未交付结果、问题、决策依据、验证证据及下一步，让后继会话能定位。
2. 核对未决依赖、原任务所有者、审查与整合状态；仍有工作时明确接续者。
3. 保全相关 worktree 的提交、未提交变更和需要保留的文件/产物，记录路径、branch/base/当前状态与恢复线索。
4. 更新会话登记中的状态、归档原因、交付位置和接续关系，再归档。

归档是可恢复操作，不是永久删除或擦除历史。会话归档与 worktree 回收分别记录；回收前也须保全成果。具体采用工具支持的归档/恢复方式，不添加没有依据的工具禁止。

| status / evidence / recovery | 分配与交付状态、测试/审查/整合证据、回收或恢复位置 |

## 5. 独立代码审查与修订闭环

所有代码变更交专门的独立代码审查 thread，作者与 reviewer 分离；总指挥只创建/调度/汇总，不能自己审核或修代码来替代该 thread。作者内部 sub-agent 的检查可以补充证据，不能作为这道审查的通过结论。reviewer 的实际 threadId 由统筹分配后登记，当前不预填虚假 ID。

审查顺序为：**作者局部实现与验证 → 独立代码审查 → 原实现会话修订 → 必要增量复核 → 确认通过 → 获授权整合**。已经审查的内容发生相关变化时，重新明确增量范围及需复核的问题，旧“通过”不自动覆盖新 diff。整合或冲突修复产生的代码变更也须按此规则审查。

| 交接 | 必须记录的内容 |
| --- | --- |
| 送审 | 作者/owner、reviewer threadId、任务、repo/worktree、base 与目标提交或精确 diff 范围；已运行的相关测试/检查、结果和未运行理由 |
| 初审 | 实际阅读范围、发现 ID/严重性、具体位置、可复现场景、影响及修改要求；无问题也说明检查范围 |
| 修订 | 原实现会话处理结果、变更提交/diff、相关验证证据、未决项 |
| 再审 | 对问题及必要增量的实际复核，明确 open/fixed/verified 或保留决定；不得只复述作者结论 |
| 整合 | 通过的范围/目标、授权范围、独立整合执行者、整合后验证及回收交接 |

执行与变更相称的测试和检查，报告真实证据，不把安排审查、模型配置或文档“verified”写成功能已实现。未关闭的阻断问题先修订/复核，之后再进入获授权整合；总指挥协调依赖，不自行修改作者代码。

原 R1/R2/R3 是已完成的 Markdown 规划审查，保留历史执行者与证据，不重做记录；它们不替代代码审查。旧治理范围的 WS07 只读核对已通过，适用范围见登记，不覆盖本次阶段授权同步或实际代码交付。
