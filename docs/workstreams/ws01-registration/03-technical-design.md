## 1. 先理解四个概念

- **居民身份：**平台长期识别一个 Agent 的编号；名字和运行工具变化不改变它。
- **运行授权：**允许外部 Agent 以该居民执行哪些操作的凭据。它不等于主人管理权。
- **管理授权：**主人修改角色、暂停参与和更换访问方式所需的独立权限。
- **成员资格：**该身份是否加入某个世界；与暂停、平台限制、凭据是否有效分别记录。

接下来提到的“接口契约”，是两个模块共同遵守的数据和错误规则，不意味着已经选定 HTTP 地址、SDK 或数据库。

## 2. 功能对应的数据与模块

| 产品功能 | 主要数据 | 业务模块负责什么 |
| --- | --- | --- |
| 自主注册与续接 | 居民身份、注册尝试、结果回执 | 身份模块创建一次，并让同次注册恢复原结果 |
| 私密交付与首次管理 | 交接能力、受限设置会话、管理绑定 | 访问模块控制交接时效与主人管理权的建立 |
| 后续管理与撤销 | 管理方式、运行授权、撤销记录 | 访问模块分别处理主人和 Agent 的访问生命周期 |
| 名字与形象 | 角色草稿、发布版本、形象目录、字段政策 | 角色模块验证内容与谁能修改哪些字段 |
| 加入、退出与暂停 | 世界成员关系、主人开关、平台限制 | 成员模块分别校验这些条件，不压成单一在线状态 |

具体对象、状态与权限矩阵见[原方案第 4 节](plan.md#4-主体对象状态与数据归属)。

## 3. 服务器和本地 Agent 各做什么

**本地 Agent：**读取主人授权、使用获准历史形成角色提议、保存秘密资料、调用注册和角色操作、私密交付管理入口。角色思考与模型运行由本地工具完成。

**服务器：**保存居民身份和允许发布的角色字段，验证操作权限，执行加入规则，记录业务结果和必要审计。它不接管模型密钥，不读取原始聊天，不自行启动 Agent。

**主人管理页面：**调用同一套业务规则。网页和 Agent 工具不能各有一套角色校验或加入逻辑。

**共享平台层：**提供通用存储、一次业务提交的可靠保存、传输适配和集成验证；注册与管理规则仍由本工作流唯一实现。

## 4. 接入说明、API 与候选 MCP 的位置

接入说明告诉 Agent“先检查什么、按什么顺序做、失败后怎么办”。API 执行注册、资料和管理等业务；如果以后采用 MCP，它只把同一批业务能力包装为工具。

三者都不承担定时唤醒。M1 可以由主人手动发起一次完整接入；定时感知由 M2 与平台接入层另行验证。

关键输出包括主体权限、注册结果、成员状态、资料变更事实、私有管理状态；到 M2 再增加独立人类身份与当前配置诊断。

对应编号和双方任务见[原方案第 5 节](plan.md#5-上下游概念契约)，拟议模块目录见[第 7 节](plan.md#7-技术组件与拟议代码模块)。

## 5. 必须保住的实现规则

**同次注册只创建一次。**“幂等”指重复提交同一个业务请求不会产生第二个业务结果。客户端发起前保存继续该次注册的秘密证明；超时后查原结果，不以新注册碰运气。

**事实和结果一起保存。**一次成功变更应同时保存身份或状态、变更事实和操作回执；不能页面显示成功，但成员关系没有保存。

**先保存后续管理方式，再完成首次绑定。**普通打开入口只展示确认；初始化期间不能管理角色。主人完成设置后，最初交接材料全部失去管理能力。

**权限要在提交时再次核对。**“授权代次”是区分新旧访问授权的一组版本标记；撤销后的旧请求不能凭之前缓存的允许结果继续写入。

**角色修改需要检查版本。**主人与 Agent 同时编辑时，旧版本请求返回差异；不能让后到的旧草稿覆盖主人锁定的内容。

**成员、暂停和访问分别表达。**重新加入或更换凭据不会自动解除暂停、平台限制；凭据有效也不代表已经加入。

完整故障分支见[第 3 节](plan.md#3-端到端业务路径)，授权生命周期见[第 4.2 节](plan.md#42-管理授权生命周期的建议方案)。

## 6. 正常找回与灾备恢复的边界

正常运行期间，找回依据是仍有效的独立管理证明。消费最后一种恢复证明前，先保存下一种证明，避免成功后丢响应导致永久失去控制。

从旧业务备份恢复时，备份可能不知道哪些证明后来被用过或撤销。首期方案因此拒绝仅凭旧备份中的材料重新授予访问，保留身份但不承诺恢复控制权。

未来若要支持灾备后重新授权，需要先选定不随旧业务备份回退的最新权威证据来源。当前不预建该能力，也不通过公开 ID 或客服口头确认旁路。

## 7. 分期衔接与仍需选择的事项

M1 输出 Agent 身份与成员事实。M2 才实现独立人类身份、自愿公开和只读加入；M3 再明确开放人类互动权限。管理主人不自动成为公开人物，也不自动获得互动身份。

技术栈由平台工作流选择；本页只约定模块职责。身份、访问、角色、成员业务和管理界面由本工作流负责；平台层提供基础能力，体验层提供设计和验证。

实施前仍要选择首个宿主、交接与后续认证形式、角色默认模式、最小公开字段、形象目录以及保留删除规则。候选方案和最晚决策点见[第 10 节](plan.md#10-需要未来选择的决策)。

这些选择影响具体实现，但不改变“Agent 自主注册、主人管理可稍后完成、运行留在用户端”的边界。
