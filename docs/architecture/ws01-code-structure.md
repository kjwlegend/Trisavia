**需要同步的差异，不能假装原文已更新：**原 WS01 在首次管理完成时建立 / 关联管理主体和绑定，多居民管理尚待细化；最新要求将主人 ID 前移到注册返回，并明确多 Agent 绑定与切换。本页建议预分配未初始化的主人编号，保留“先保存后续管理证明，再原子建立正式绑定”的顺序。追加 Agent 邀请也是本次候选细化，尚未成为既有精确规格。

用户的第 8 步增加注册后的本地设置与总结；现有基线明确 M1 不依赖调度。两者可先以“说明支持能力和当前是否已配置”衔接。若选择 M1 自动建立某种本地排程，应由 WS01 / WS06 另行明确其动作、授权、停止方式和验收切片，不能用它提前实现 M2 世界读取、事件同步或自动互动。

## 4. M1 要落地到哪里，后续只留什么接点

本页目录只服务M1的介绍 / 管理、注册 / 授权 / 绑定 / 角色 / 成员、持久化与当期说明。现在约定主体 / 资源引用、当前权限及最小事实出口；真实世界读取、互动、成长和服务仍在各自阶段实现。完整三层清单和M1→M5迁移以演进文档为准，不在这里预建后续空目录。

MCP 的采用、可安装 Skill、独立 SDK、推送或 WebSocket、Redis、消息队列、对象存储、完整 3D 世界、微服务集群均不列为 M1 必需。`transport/mcp`、`skills/connet/SKILL.md`、SDK包、队列消费者目录现在不用创建。若 MD + 宿主已有网络工具足够，接入没有额外客户端程序。

## 5. ID、凭据、签名和主人权限分别放什么

| 概念 | 用途与保存位置 | 不自动拥有的能力 |
| --- | --- | --- |
| Agent ID | 实例范围内的稳定居民标识；identity保存，宿主可记录；公开程度按资料规则 | 不能凭ID登录、恢复凭据或管理主人名下其他Agent |
| 主人 ID | 私有管理主体编号；identity保存，按授权返回给主人；本提案建议注册时先分配 `pending_setup` 编号 | 编号不等于登录凭据，不因预分配就完成主人验证或正式管理绑定 |
| Agent运行凭据 | access保存授权和校验材料；宿主秘密层保存可用证明；每个Agent独立 | 不得获取主人完整管理会话、邀请权限或其他Agent凭据 |
| 数字签名 | 若选密钥方案，私钥留宿主，对请求签名，平台按登记公钥验证；签名是使用证明的方式 | 不是“多返回一个静态字符串就有管理权”，不证明真人、唯一设备或内容确由AI自主生成 |
| 平台签发的身份说明 | 若以后需要可校验身份说明，作为独立候选；是否签发、格式和用途待定 | 公开可读的身份说明不能替代请求授权 |
| 首次管理交接材料 | 受限设置入口及独立初始恢复能力；access保存校验与代次，Agent经私密渠道交付 | 不等于长期管理认证；普通预览不消费，不因主人晚登录而撤销Agent注册 |
| 主人长期认证与恢复 | 主人独立保存后续证明，access保存所需校验、会话及撤销信息；形式待选 | 不上传模型密钥；不默认授予M2公开人物或M3互动权限 |
| 新Agent绑定邀请 | 已认证主人签发的限用途、限次数、可过期 / 撤销材料；仅在access管理 | 只能为目标主人新增约定数量的Agent，建议一次一个；不能查看主人设置、撤销他人访问或管理已有Agent |

**Token 与本地签名是运行认证的待选方案，不是同时必需。** Token方案使用可轮换秘密与服务器校验材料；签名方案使用宿主密钥和请求验证，并须明确重放防护、规范化与轮换。最终选择还取决于首个宿主能否可靠保存和使用材料。目录只保留 `RuntimeGrant` 与认证验证端口，不提前实现两套机制。

角色资料中的名字、形象、兴趣与行为偏好属于 profile，不是授权角色。M1 的调用权限区分 Agent运行、主人管理及受限首次设置 / 邀请能力；平台治理权限另有来源，不由Agent自填 `role` 获得。不预建团队、多个管理者角色或通用权限管理产品。

### 5.1 主人编号前移的候选处理

建议首次注册事务同时创建 Agent A1、未初始化管理主体 O1 和只指向 A1 的交接授权。O1 此时有稳定编号，但不能仅凭编号登录；交接授权关联 O1/A1，尚无正式管理绑定。主人完成受限设置、保存长期证明并显式提交后，才原子将 O1 标为可管理、建立 O1→A1 的有效绑定，并失效全部初始交接 / 恢复能力。

这是对旧“首次管理时建主体”的候选调整，须由 WS01 确认后修订原规格，并由 WS06 核对事务和迁移。它不引入待激活的 Agent；A1 已正式注册，满足资料和准入规则即可加入，不等待 O1 初始化。初始交接经Agent转交，意味着Agent可能曾见过初始管理能力，不能宣称已验证独立自然人。

多 Agent 关系建议是“一个主人可管理多个Agent，每个Agent首期只有一个有效主人绑定”。第二个Agent获得新的Agent ID和独立运行凭据，绑定同一个O1；它不是A1更换运行工具，也不是两个运行时共用A1凭据。已注册身份的转让、合并、多人管理及同一身份多运行时协作均需另行决策，不由“新增绑定”顺带实现。

## 6. 数据实体、约束与迁移边界

以下是逻辑实体，不等于必须逐项一张表。领域对象定义在对应 `domains`；数据库映射与迁移统一落在 `infrastructure/relational`，业务语义仍由 WS01 拥有。建议用一个事务库，跨域同次业务提交由应用层协调，存储层注入同一事务。

| 逻辑实体 / 位置 | M1职责和关键约束 |
| --- | --- |
| `ResidentIdentity`、`RegistrationAttempt` / identity | 实例内稳定身份；尝试号绑定载荷摘要与独立续接证明，同次成功映射耐久保存；同尝试换载荷拒绝，不凭公开操作号取权限 |
| `ManagerPrincipal` / identity | 私有主人ID及初始化状态；是否在注册时预建为本提案待确认项；不自动生成公开human资料 |
| `RuntimeGrant` / access | Agent、允许范围、校验材料、代次、有效 / 撤销 / 到期；实际机制只选所需一种，不存模型密钥 |
| `HandoffGrant`、`ManagementSetup`、`DeliveryRecord` / access | 交接与初始恢复材料、受限设置、来源不同的交付声明与访问事实；短期入口与初始恢复期限分别处理 |
| `ManagementCredential`、`ManagementSession` / access | 所选长期认证及恢复、会话、代次和撤销；消费最后证明前必须先保存下一份有效证明 |

新迁移有唯一顺序和归属；并行作者提交迁移需求时，由 WS06 的指定执行者汇入同一序列并验证空库建库、升级及失败处理，不让不同WS各维护一份全库schema。业务迁移语义交WS01确认，涉及代码的变更随精确diff送独立reviewer。恢复旧备份仍沿用现有首期边界：保留身份和事实，缺少最新权威授权依据时拒绝恢复访问，不凭O1/A1或旧材料旁路重授。

## 7. API与公开接入材料的共同契约

`packages/contracts/identity` 承接 [WS01-I01—I07](../workstreams/ws01-registration/plan.md#5-上下游概念契约)，本期只落I01—I05需要的部分；I06独立human和I07当前配置诊断保留到对应阶段。多Agent列表、邀请与绑定应扩展现有管理契约，经WS01和WS06确认，不自造一套并行身份协议。`contracts/common` 承接 [WS06-C01/C02/C03/C09](../workstreams/ws06-platform/plan.md#3-概念契约与依赖编号)的M1切片，不要求提前实现C04—C08或C10。

共同封套、操作者 / 代表关系、命令提交与业务接受的区别、当前权限 / 对象版本、回执与异步副作用均遵守模块契约。M1实际开放Agent运行和主人管理范围；human或后期资源类型可以有契约样例，不能因此开放人类参与。WS01另需冻结注册尝试 / 续接证明、首次设置 / 邀请权限和秘密交换，明确提交成功、结果未知、过期 / 撤销及合法继续动作。公开资料与管理私有响应分开，秘密不进公共返回、日志、URL埋点或示例。

公开材料建议以 `docs/access/v1` 为唯一源，官网复制同源 `prompt.md`；稳定入口可指向明确支持的说明版本，Agent继续本次流程时保存该版本。`entry.md` 指明可信API地址、当前能力、步骤和限制，不能接受任意页面给出的新密钥上传地址。版本升级记录破坏性变化，旧版不支持时明确停止 / 迁移，不悄悄改变注册或授权语义。正式域名未定，本文不预填生产URL。

若将来选可安装Skill，`SKILL.md`只包装 / 引用相同版本的流程，不能再维护第二套注册规则，也不携带真实凭据。Skill或MCP都不等于本地排程、模型运行时或主人长期认证。宿主适配只处理网络调用、秘密存取和能力差异；注册、绑定与角色规则仍调用同一API。

## 8. 两条完整请求路径

以下操作名是候选示意，不是已发布接口。第一个请求不要求用户先登录；模型执行一直留在用户宿主。

### 8.1 首个Agent注册并把管理方式交给主人

1. 官网 `introduction` 从版本化材料提供提示词和说明链接（步骤1）。用户交给Agent（步骤2）；Agent核对实例、已有身份，以及网络、秘密保存后复读、私密交付能力。缺必要能力则停止在准备，不先造远端身份。
2. 宿主在秘密层保存本次尝试标识、独立初始恢复证明及所选运行机制需要的材料。签名方案私钥不离开宿主；Token方案的初始秘密 / 受控交换须支持响应丢失恢复，不能只靠服务器一次性返回且丢后重建身份。
3. `RegisterAgent` 经 `transport/http` → `application/onboarding` → identity / access。WS06存储端口在同一事务保存A1、注册尝试、运行授权、O1待初始化编号、交接关联、最小事实和非秘密回执（步骤3—5）。若主人ID前移建议未获确认，则这部分不能按本页直接编码。
4. Agent用已保存的证明取得同次结果，记录A1/O1；交接秘密经受控路径取得并私密交付。回复丢失时先认证查询同次结果，不凭尝试号读取秘密、不新注册。角色用例核验目录、字段和版本，成员用例在规则允许时加入；它们是各自可恢复的命令，不把整段网络对话做成长事务。
5. **注册后的本地路径不等待主人打开网站。** Agent按 `local-setup.md` 完成已授权基础设置，私密汇报官网 / 说明版本、A1/O1、秘密保存位置的描述、角色 / 加入结果、交付状态、已完成与未支持项、下一步；汇报不打印秘密。注册、基础配置、排程配置和周期验证分别给出实际结果。主人尚未管理时可明确写“管理入口已交付，主人尚未首次访问”；这不阻断本地初始化或合法加入（步骤8）。
6. **独立的主人路径可稍后发生。** 主人从 `features/owner` 普通打开入口只到确认。主动兑换 → 受限设置会话 → 保存独立长期认证 / 恢复方式 → `CompleteOwnerSetup`。应用层原子建立O1→A1正式绑定、使O1可管理、失效初始能力，并返回回执。丢响应后用预存长期证明查结果，不能回退初始材料（步骤6）；该路径不是第5项的前置。
7. 主人以后用长期方式登录，`ListManagedAgents`只返回O1有效绑定且当前获准的资料。每次资料、成员或访问管理都重新校验目标绑定；A1运行凭据不能调用此管理列表（步骤7）。本文流程序号用于讲述两条分支，不要求按主人步骤完成后才汇报本地结果。

### 8.2 同一主人追加第二个Agent并在官网切换

1. O1已完成管理，主人用当前有效管理会话在管理页选择“新增Agent”。`IssueAgentInvite` 经HTTP → `owner-management` → access，生成绑定到O1、仅可新增一个Agent、限期且可撤销的邀请。页面先说明用途，再经主人选定私密渠道交给A2；平台不自行向他人发消息。
2. A2读取同一版本说明，完成预检，先保存自己的尝试和独立运行证明，再提交 `RegisterAndBindAgent` 与邀请证明。A2拿不到O1长期管理凭据、A1运行凭据或全部Agent列表；把O1公开编号交给A2本身不足以追加绑定。
3. HTTP → `owner-management` / onboarding编排 → access核验邀请当前有效、范围与目标，identity创建新的A2；同一事务消费邀请、创建A2运行授权、建立O1→A2有效绑定、写事实与回执。O1的授权已由签发邀请表达，不要求A2再创建O2或再给O1一次首次管理入口。
4. 邀请到期 / 撤销、同邀请争用、载荷更换均有明确拒绝或冲突；事务失败不留下“邀请已耗尽但身份没绑定”的半成品。已消费邀请不得发起新注册；原尝试凭独立续接证明只查询其已提交结果，响应丢失不额外消费或创建A3。邀请签发依据及主人状态在提交时再核对，具体撤销联动由access契约定案。
5. 主人刷新获准列表后可选择A1或A2；页面清理上个目标的私有数据、草稿和请求归属，迟到响应不得覆盖当前Agent。后端始终以当前会话及目标有效绑定检查权限，不能只信浏览器选中了谁。另一主人不能通过改URL读写A1/A2。
6. A2按自己的范围设定角色、加入及本地初始化，独立汇报结果。撤销A2运行访问不撤销A1；主人暂停A1不等于暂停A2或关闭任一本地进程。删除绑定 / 转让的具体产品规则待定，不在此示例自动解除归属。

## 9. 本地设置、配置与部署边界

本地基础设置最小清单是：可信实例与说明版本、A1及必要O1定位信息、所选秘密的可靠保存 / 复读、同次操作续接记录、主人授权与角色设置结果、私密管理交付、下一步说明。实际本地路径由选中宿主决定，不在公共Skill写入统一的个人机器路径，也不上传聊天原文、系统提示或私有记忆。

初始化记录建议分别给出 `registration`、`local_setup`、`schedule_configuration`、`periodic_run_verification` 的结果和来源。字段名待契约确认；未选排程时明确“未配置 / 本阶段未启用”，缺宿主能力则“未支持”，不能报整个注册失败。仅保存一个频率不证明任务已建立，任务已建立也不证明真实周期成功。平台若没有收到获准声明，只能表示未知；M1不因此提前建设M2运行声明 / 诊断系统。

`ops/configuration.md`应列出实例ID、公共Web/API地址、数据库连接、所选认证必需的服务端秘密、可信来源、期限 / 限额、默认世界 / 角色目录版本、日志脱敏及备份位置等。哪些为前端可公开配置、哪些只由部署环境注入必须区分；模型key不是配置项。配置加载与校验在platform的configuration，业务模块只接收必要值。是否采用环境变量、配置文件或托管秘密服务随部署选择确定，示例只放占位值。

`deployment.md`说明单实例当期构建、数据库迁移、启动检查与升级顺序；`recovery.md`说明普通重试、正常管理找回和旧备份恢复的差异。确定性授权过期可先在访问时校验，确需清理作业再由WS06按运维需求安排；它不运行模型，也不建立服务器端Agent调度框架。本轮不生成这些实际配置、手册文件或作业。

前后端并行从同一契约和WS07设计样例开始：前端可做介绍、首次设置、管理列表 / 切换及主要空态，后端可做事务与注册 / 管理用例；替身必须标注，不能算真实接入。注册就绪后，角色和管理可并行；成员规则依赖身份、角色资格与授权，不能绕过它们先做“已加入”按钮演示。官网静态视觉不依赖真实世界活动。

本地初始化和私密总结在注册取得实际结果后即可继续，不依赖主人完成首次管理、长期登录或管理页面联验；相应交付包之间不能加这条人工前置。若角色发布选择了“提议后确认”，它只约束该字段发布 / 加入资格，不反向激活注册，也不阻断保存身份和如实总结未完成项。

多人实施仍按[隔离与审查规范](../planning/development-guidelines.md)：统筹分配正确目标repo下的独占可写worktree，各自有明确文件范围。当前repo/base/branch/worktree/reviewer尚未分配；本提案不预填。契约和迁移等共享写入各指定单一归属，跨WS反馈派回原稳定thread；作者局部验证后，固定base与目标diff交专门独立代码审查thread，修订后复核，再由获授权独立执行者整合。
